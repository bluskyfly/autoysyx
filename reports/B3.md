# B3 — 时序分析和优化

B3 章节正文标注 "建设中, 但暂无编程内容"。本笔记总结本项目里和 STA / 时序相关的实际工作。

## 我们做了哪些和时序相关的事

```
            yosys check (在 npc/Makefile 中)
                │
                ▼
       检查 latch / multidrive / 多余 driver
                │
                ├─ ysyx_22040000 (DPI harness top)
                ├─ cpu          (D4 单周期 top)
                └─ ysyx_22040000_bus (B1 SimpleBus full-handshake)
                │
                ▼
       三个 top 全部 clean (no latch / no multi-drive)
```

具体在 `npc/Makefile` 的 `yosys-synth` target 下，调三个 yosys 脚本：
- `npc/syn/synth_soc_top.ys`
- `npc/syn/synth_cpu_top.ys`
- `npc/syn/synth_bus_top.ys`

每个脚本执行：

```
read_verilog -sv <顶层 + 子模块>
hierarchy -check -top <top>
proc; opt; check -assert
stat
```

`check -assert` 在以下情况下报错：
- 有 inferred latch (RTL 写得不对，组合循环或者 always block 漏 default)
- 有 multiple drivers (同一信号被两个 always block 驱动)

我们目前的 RTL 通过这些 lint，说明设计上没有结构性的时序隐患。

## 真正的 STA 需要什么

如果要做"无负 slack"分析，需要：

```
RTL (Verilog) ──┐
                ├─► 综合 (yosys + abc + PDK liberty)
                │           │
                │           ▼
                │   Gate-level netlist (Verilog)
                │           │
                │           ▼
SDC 约束 ──────► OpenSTA / PT
                │           │
                │           ▼
                │   slack 报告 (setup/hold)
```

约束文件 (SDC) 关键内容：

```tcl
create_clock -name clk -period 10.0 [get_ports clk]
set_input_delay  -clock clk 0.5 [all_inputs]
set_output_delay -clock clk 0.5 [all_outputs]
set_load 0.05 [all_outputs]
set_driving_cell -lib_cell BUFx2 [all_inputs]
```

预期分析点：
1. **关键路径**：单周期 NPC 的关键路径在 `IFU.pmem_read → IDU → EXU.alu_op → WBU.regfile_wen`，长度大约 30-50 cell delay。
2. **PC 更新**：跳转判断 (`branch_taken` from EXU) 到 PC 寄存器输入端，是另一条 critical path。
3. **CSR 写**：`csr_we_dec` 到 CSR mtvec / mepc 寄存器，会被 mret/ecall 频繁触发。

## 现状评估（无负 slack 的判断标准）

因为本项目没有签约商业 PDK，无法做物理 STA。所以"无负 slack" 退化成下面这些约束：

| 检查项 | 状态 | 说明 |
|--------|------|------|
| RTL 没有 latch | PASS | `yosys check -assert` 在三 top 上都通过 |
| RTL 没有 multi-drive | PASS | 同上 |
| RTL 没有组合环 | PASS | yosys synth 没报循环 |
| CPU 单周期，关键路径已知 | PASS | D4 报告里画过数据通路图 |
| Bus 端 6 状态 FSM 收敛 | PASS | B1 沙盘测过随机延迟，没死锁 |

ysyx 流片考核会跑专门的工具链 (DC + PrimeTime + EDA 测试套件)，我们这边的 RTL 通过 lint 是必要不充分条件。

## ysyxSoC 顶层综合警告

顶层 `ysyxSoCFull.v` (vendor 生成) 综合时会有一些 vendor 自带的 warning，例如 ChipLink 的 BlackBox 引用、APB delayer 的多 always 块等。我们不修改顶层 v 文件，这些 warning 不在 B3 范围内。

## 已知遗留 / 后续工作

- 当 NPC 扩展到流水线 (B5)、加 cache (B4) 之后，关键路径会重新分布，需要再跑 lint
- 实际流片时 STA 报告由"一生一芯"项目组提供，自行只能跑 lint 保证一阶段干净
- 如果未来引入 SystemVerilog assertion (SVA)，可在 yosys formal flow 里跑一些功能验证

## 结论

B3 文档本身无编程内容。我们项目当前对应 STA 的 RTL 端工作 (lint + 结构检查) 已经通过 B1/B2 工作期间持续维护。下一步真正的"无负 slack"分析需要工业级 EDA 工具链，超出本项目范围。
